## Objective
From the DevOps review: a crashed app or a PC restart left the shop down until someone clicked
Shop. Failed backups were silent, logs were never deleted, and no PC settings were checked.

## What changed
| Area | Files | Behaviour |
|---|---|---|
| Watchdog | `local-server\watchdog.ps1` (new), `install-autostart.ps1` | Task "RS Inventory - Watchdog" runs every 5 min. It is registered as S4U (runs with nobody signed in) when the window is Administrator, otherwise as Interactive with a warning. An environment is watched while `run\<env>.json` exists (start.ps1 writes it, STOP.bat removes it). If `/api/version` fails 3 times, the watchdog restarts the environment in the same mode. A failed restart puts the run file back so the next round tries again. `-NoWatchdog` removes the task. |
| Update lock | `common.ps1` (`$MaintenanceFile`), `update.ps1` | `run\maintenance.txt` exists during an update, and the watchdog skips while it does. Ignored once it is older than 3 hours. |
| Monitoring pings | `common.ps1` `Send-Ping`, `backup.ps1`, `restore-test.ps1`, `watchdog.ps1`, `*.example.env` | Optional `MONITOR_PING_URL`, `MONITOR_BACKUP_PING_URL`, `MONITOR_RESTORE_TEST_PING_URL` (healthchecks.io style: `<url>` or `<url>/fail`). The body holds the app version, PC name, free disk and the status text, never shop data. When fewer than 5 GB are free on the data drive, the heartbeat ping is sent as `/fail`. |
| Log cleanup | `common.ps1` `Remove-OldLogs` | Deletes logs not written for `LOG_KEEP_DAYS` (default 30). Runs in the nightly backup and in the watchdog. |
| PC checks | `check.ps1` | Notes (never blocking) for: sleep or hibernate on mains power, Fast Startup, DHCP address, blank `BACKUP_COPY_DIR`, blank `MONITOR_PING_URL`, missing watchdog task. |
| In-app status | `app\api\src\lib\server-backup-status.ts` (new), `routes\backup.ts` `GET /api/backup/server-status` (backup.manage), `env.ts` (`BACKUP_STATUS_FILE`, `RESTORE_TEST_STATUS_FILE`, set by `start.ps1`), `app\web\components\ServerBackupStatus.tsx` (new), Backup page, dashboard | The Backup page shows the last nightly backup and the last restore test. The dashboard shows a red box only for CLIENT_READY when the last backup is missing, FAILED or older than 26 h, or when the restore test FAILED or is older than 8.5 days. Hosted installs (no status files) show nothing. |
| Docs | `README.md` ("Keep the shop PC running", "Monitoring"), `install-all.ps1` step label | Owner checklist and healthchecks.io setup. |

## Decisions
- No third-party service wrapper (NSSM/WinSW): that would mean a binary download, and Task Scheduler with S4U does the same job.
- The watchdog restarts only what was running. During the V2 production test, V3.1 is still not started at sign-in, but if it was running when the PC restarted, it comes back.
- The backup and restore-test tasks keep their Interactive principal (unchanged): S4U has no network credentials, so a `BACKUP_COPY_DIR` on a network share would break.

## Not done / known limits
- `install-autostart.ps1` not run on a real PC (S4U registration is untested here; it needs Administrator).
- `backup.ps1` / `restore-test.ps1` pings not run end to end (no PostgreSQL for the scratch env). They use the same `Send-Ping` that was tested.
- A log file stays open for as long as its process runs, so one very long run still grows one file. A real service wrapper would fix that.
- Demo seed: there is nothing to seed (the status comes from files, not the database). Demo shows "Not run yet" with a note. `BUILD-DEMO.bat -KeepData` not run: it always builds the main `measurement-inventory\` checkout (another branch), so the production `next build` above was run in this worktree instead.
- Off-site encrypted backup (restic/rclone to B2/R2) left for the owner to choose.
