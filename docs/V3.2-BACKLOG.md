## A. New owner requests (2026-10-24)

### A1 (P1) Backorders visible from sale to purchase

Today a backorder lives on the sale order page only ("Shortage & Procurement Tracking", "Arrange
purchase"). The data already exists: `getShortagesAndProcurement` (`api\src\lib\measure.ts`),
purchase lines linked to sale-order lines (`linkedOrder*`), and covered/uncovered quantities.

Build:
1. **Backorders page** (Orders → Backorders): one row per item still short across all open sale
   orders — item, total short (qty or length), sale orders waiting (SO numbers, customers, dates),
   covered by (PO numbers, supplier, expected date), uncovered rest. Filters: supplier, category,
   warehouse, "uncovered only". Action **Arrange purchase** for the ticked rows → one purchase cart
   per supplier (best vendor rate pre-selected, never auto-saved).
2. **Purchase side:** product cards and the purchase drawer show "Backorder: 12 m for 2 customer
   orders"; a PO page lists the sale orders it covers; receiving a linked PO shows "Now ready to
   deliver: SO/…" with a link.
3. **Sale side:** sale order line shows "Waiting for PO/… (supplier, ordered on …)".
4. Dashboard / Stock In badge "N backorders" (uncovered count).
5. Fill the known gaps: whole-set backorder (no set in stock at all — currently not offered),
   held drafts keep the purchase-line link, remove or use the unused
   `POST /api/orders/:id/arrange-purchase`, re-save old orders whose `order_lines.sets` hold milli lengths.

Tests: integration test for the backorder list (counted, measured, set part), PO cover, receipt.

### A3 (P1) Vendor pricing for grouped products (was D24 "V4")

**Done 2026-10-28 (uncommitted).** Owner decisions: parts sum + per-supplier set rate override; the
override is per set type; set purchases update it on Complete; no margin for now. Built without a
new table: the set rate is a `vendor_prices` row on the grouped product's own variation. Purchase
set sheet shows supplier set rates (tap fills every set) and "From parts ₹X" per row; Supplier
Rates lists set rows as "₹ per set". Not done: margin, part breakdown on the Supplier Rates page.
Original proposal below.

Owner now wants it in V3.2. Proposal to confirm:
- **Computed rate**: a set type's supplier rate = sum of its parts' supplier rates (chain by length
  × rate per unit, hook, body), shown as "from parts".
- **Set rate override**: a supplier may quote a whole set; stored per supplier + set type
  (`vendor_set_prices`, history like `vendor_price_history`). Override wins over computed.
- Shown in: Supplier Rates page (set rows with part breakdown), purchase set sheet ("Vendor: ₹min–max ·
  N suppliers", cheapest first, tap to fill — like counted items), set purchase lines update the
  override on Complete (same rule as other lines).
- Open questions: one rate per set type or per exact contents? Does a sale price per set use it for
  margin? Mixed rates on one cart line (cart already splits by rate).

### A8 (P1) GST / Non-GST product tag + Tally export

Owner request (2026-10-24):
1. **Two product types: GST and Non-GST.** The create-product form asks "GST or Non-GST" (required,
   no default, so nobody skips it); the choice is a tag shown on product cards, the Products list
   (filter), the product page, cart lines and documents. Editable later by admin, with an audit entry.
   GST products also take HSN/SAC code and GST rate (0 / 5 / 12 / 18 / 28 %); Non-GST products do not.
2. **Tally-format export for GST products**: export sales / purchases (and the product + party
   masters they use) from the software as a file Tally Prime can import — Tally XML
   (`ENVELOPE` → `TALLYMESSAGE` → `VOUCHER` / `STOCKITEM` / `LEDGER`), optionally Excel in the same
   layout. Filters: date range, voucher type (Sales / Purchase), GST products only. Each voucher:
   number, date, party ledger + GSTIN + state, items with HSN, qty, rate, taxable value, CGST/SGST
   or IGST ledgers, round-off. A dry-run screen lists missing data (party without GSTIN/state,
   product without HSN/rate) before the file is made.

Scope warning: this brings GST into V3.2 — today the party profile has no GSTIN / PAN / state
(schema note "no GSTIN/PAN/state until V3", owner decision 4), and invoices have no tax lines.
Agree with the owner: which GST fields come first (product tag only, or full tax on invoices); mixed
GST + Non-GST lines on one bill (split into two bills, or one bill with separate totals); ledger
names to match the shop's Tally company; Tally Prime version used by the accountant.
DB: `product_groups.tax_type` (`GST` | `NON_GST`), `hsn_code`, `gst_rate`; party GSTIN / state —
migration 0039+ (shared with A2).
